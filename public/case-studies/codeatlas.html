Why build the harness first

A retrieval demo is easy to make and impossible to trust. You type a question, you get plausible results, and you have learned nothing about whether the system works on the questions you have not thought of. So the first thing built here was not the retriever, it was the thing that scores it: 36 questions across four codebases with the answering files labelled by hand.

Two rules decided whether the set would measure anything. Questions are phrased the way someone new to the repo would ask, "what stops the relays flickering when my hand shakes slightly", not "find the jitter threshold". A question that reuses the codebase's own identifiers tests string matching and flatters lexical search. And every file that genuinely answers a question is labelled, not just the first one that came to mind, because under-labelling shows up later as a false failure and costs an afternoon.

Relevance is judged at file level: a retrieved chunk counts if its source file is one of the labelled answers. That is more generous than passage-level judging. It is also reproducible, which matters more at this size.

The result I did not expect

The hypothesis was that splitting code on declaration boundaries with Tree-sitter should beat sliding a fixed window over it, because a window cuts functions in half and half a function retrieves badly.

The first run said the opposite. Structural chunking scored recall@5 0.72 against the window baseline's 0.81. The clean conclusion would have been that the idea does not work.

It was not a clean experiment.

Structural chunking produced 819 chunks at a median of 9 lines. The window baseline produced 403 at a median of 40. Two variables moved at once, so the result could not separate boundaries in the wrong place from chunks too small to carry meaning. A nine-line method embedded on its own is mostly a signature.

Merging adjacent declarations up to a 25-line minimum, without ever splitting one, gives 371 chunks at a median of 36 lines. Same shape as the baseline. Now only the boundary policy differs:

Boundaries help ranking, not recall. The right file reaches the top five either way. Structural boundaries make it more likely to be first, which is what matters when the context budget is five chunks rather than fifty. And chunk size mattered more than boundary policy: getting size wrong wiped out the boundary gain and then some.

The reranker made it worse

Reranking the top 30 with a cross-encoder is close to standard advice, and ms-marco-MiniLM-L-6-v2 is the obvious one to reach for. Here it cost MRR on both chunkings: 0.554 down to 0.520 on merged structural chunks, 0.515 down to 0.458 on windows.

That model is trained on MS MARCO, which is web passages in natural language. Code is out of distribution for it, and a reranker that is confidently wrong is worse than none at all, because it reorders results the first stage already had roughly right. A code-trained reranker would likely help. Shipping this one because the architecture diagram looks more complete would have been the wrong call, and without the harness I would not have known.

Where it fails, and what that cost

Seven of 36 questions still miss at rank five. Reading them produced two failure modes, and both turned out to be measurable rather than impressionistic.

that is documentation, not code0.460.29

Documentation crowds out code. READMEs are written in the same register as the questions, so they sit closer in embedding space than the code that implements the answer. Ask "where is job state stored so the API and the worker both see it" and all five results are README sections, while the repository class that answers it sits below the cut.

Nothing scopes the query to a project. The corpus holds four separate projects. "Is anything stopping one client from hammering the API" is a reasonable question about two of them, and the retriever has no way to know which one is meant.

There is a third mode that no amount of ranking fixes. "What kinds of report can this produce" needs the complete set, spread across four files. Retrieval is a similarity function, not an aggregation, and asking it for an exhaustive list is asking the wrong thing of it.

The fix that came out of reading the failures

The first mode has a small fix: cap how many chunks any single file may contribute, so one long README cannot occupy the whole context window. Overflow is pushed below the survivors rather than discarded.

About ten lines, for +0.11 recall@3 and +0.037 MRR. It came from reading what the system got wrong, not from tuning parameters until a number moved. That is the argument for building the harness before the retriever.

How it works

files ──► chunker ──┬─► BM25 index          ┐
                    └─► MiniLM embeddings   ├─► RRF fusion ─► per-file cap ─► top k
                                            ┘

Tree-sitter splits Python and Java on declaration boundaries, one chunk per function, method or class, with the enclosing scope kept in the chunk name. Markdown splits on headings and the heading path is prefixed onto the text, so a section called "Retries" nested under "Fault Tolerance" is findable by either term. Imports and module-level constants become a preamble chunk rather than being dropped, because "what is the retry limit" often needs exactly that.

BM25 tokenization splits identifiers as well as words, so RateLimitFilter is reachable from "rate limit". Fusion is Reciprocal Rank Fusion rather than a weighted blend, because BM25 scores and cosine similarities are not on a comparable scale and normalising them introduces a weight nobody can tune honestly against 36 questions.

What I would do differently

  • 36 questions is a small set. A five-point gap between two strategies is within noise at this size, which is why the conclusions above lean on the differences that are large and consistent across chunkings rather than on any single cell. Two hundred questions would let me put intervals on this, and I would trust the reranker result more.
  • I wrote both the questions and the code being searched. That is the cleanest way to get honest labels at this scale, and it is also the obvious bias: I already know what the answer files are called. Questions from someone who has never seen the codebase would be harder and more realistic.
  • File-level relevance is generous. A chunk from the right file counts even when it is the wrong function in that file. Passage-level judgements would be stricter and would lower every number here.
  • No generation, so no faithfulness measurement. This evaluates retrieval only. Retrieval quality bounds answer quality, so it is the right thing to fix first, but whether a model's answer actually follows from the retrieved context is a separate measurement I have not made.
  • Project routing is the obvious next fix. The wrong-project rate more than doubles on failures. A cheap classifier over the query addresses more of the remaining gap than further ranking work would.
